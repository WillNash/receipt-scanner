# Plan Review

## Verdict
**APPROVED** — the plan is sound and implementation can begin, with the clarifications and corrections noted below. None of the flaws are blockers; they are precision issues that the implementer should resolve in-line.

---

## Flaws Found

- **Flaw 1 — Aurora Serverless v2 scale-to-zero characterisation in plan preamble is slightly imprecise:** The plan's "Assessment: What Is Accurate and Strong" section says "Aurora Serverless v2 scale-to-zero engine version requirements ... are correct." However, the researcher document notes that Aurora Serverless v2 "does not scale to zero" unless minimum ACU is explicitly set to 0, and the v2 feature for true zero (auto-pause) is a relatively new addition tied to specific engine versions. The skill already captures this correctly ("Scaling to zero (auto-pause) requires explicitly setting minimum ACU to 0 and a supported engine version"), so the plan's assertion that this is correct is itself correct. However, the plan then calls out the "~$43/month always billed" figure as a staleness risk in Flaw Item 1. What the plan does not note is that the CloudFormation snippet in the researcher document sets `MinCapacity: 0.5` (not 0), which is inconsistent with a "scale to zero" example but is actually the correct production default. This inconsistency in the researcher doc does not affect the plan's instructions but is worth noting so the implementer does not copy that snippet verbatim into the skill.

- **Flaw 2 — Step 2 names "AgentCore" without a caveat about its novelty and limited production footprint:** The plan instructs adding "AgentCore for production agents" in the Bedrock section. The researcher document confirms AgentCore is a 2025 GA service. However, the researcher also notes that Bedrock Agents already exists for agentic loops and tool use, and AgentCore is the newer, higher-level construct. Including AgentCore without distinguishing it from Bedrock Agents (the existing, widely-adopted service) risks creating ambiguity in the skill. A senior SA should know that most production agent workloads in 2025 still use Bedrock Agents directly, and AgentCore is the emerging path for complex, long-running autonomous agents. The plan does not flag this distinction, so the implementer may write the Bedrock section in a way that over-promotes AgentCore and confuses users who are using the older Bedrock Agents API.

- **Flaw 3 — Step 10 states the Database Savings Plan discount as "up to 35%" for all five covered services, but this figure is not uniformly accurate across services:** The researcher document confirms "AWS Database Savings Plan (launched December 2025) covers RDS, Aurora, DynamoDB, ElastiCache, DocumentDB (up to 35% savings)." The plan repeats this figure without nuance. In practice, the savings rate varies materially by service and commitment term — DynamoDB on-demand can receive a different discount rate than RDS, and 35% is the ceiling figure for specific combinations, not the typical outcome. The plan should direct the implementer to include the "up to" qualifier and a note to verify current rates by service at the AWS pricing page, not present 35% as a uniform rate. This mirrors the same staleness risk called out for the Aurora dollar figure in the plan's own Flaw Item 1, but the plan does not apply the same self-awareness to the Savings Plan discount number.

- **Flaw 4 — Step 7 conflates two separate mechanisms under "Route 53 ARC":** The plan's Step 7 instructs adding: "Route 53 ARC (Application Recovery Controller) and Global Accelerator." The researcher document confirms both are correct, but it also clarifies that ARC uses Route 53 as a data-plane switch — meaning ARC orchestrates Route 53 routing policies, it does not bypass DNS. Global Accelerator, by contrast, truly bypasses DNS TTL issues via Anycast IPs. The plan's wording ("Route 53 ARC and Global Accelerator") groups them as equivalent data-plane mechanisms, but they work differently: ARC is an orchestration layer over Route 53 health checks (which still propagate DNS), whereas Global Accelerator's Anycast routing is genuinely TTL-independent. If the implementer writes the skill section based on the plan wording, users may incorrectly believe Route 53 ARC itself eliminates DNS TTL delays. The skill needs to make clear that Global Accelerator is the TTL-independent mechanism, while ARC is the orchestration framework for controlled Route 53 failover. This distinction is in the researcher document but the plan's step wording does not surface it clearly enough to guide the implementer.

- **Flaw 5 — Step 14 characterises EventBridge Scheduler as replacing "CloudWatch Events rules for scheduling" without noting the actual migration path for existing resources:** The plan says "EventBridge Scheduler ... Preferred over CloudWatch Events rules for all new scheduled workloads." This is correct per the researcher document. However, the plan does not note that CloudWatch Events rules are now exposed through the EventBridge console as the "default event bus" and that the conceptual rename is EventBridge (not a distinct new service UI). An implementer writing the skill could create confusion by saying "EventBridge Scheduler replaces CloudWatch Events" in a way that implies EventBridge event bus rules and EventBridge Scheduler rules are the same thing — they are not. EventBridge Scheduler is a distinct resource type (schedules, not rules) with its own API and separate DLQ configuration. The plan step should be more precise: EventBridge Scheduler (schedules with cron/rate) replaces CloudWatch Events scheduled rules; EventBridge event bus rules (which are what CloudWatch Events became) are still the right tool for event-pattern matching and routing.

- **Flaw 6 — Missing topic: "Amazon Q Developer" (formerly CodeWhisperer) is in the researcher document but is absent from both the plan and the skill:** The researcher document explicitly calls out "Amazon Q Developer (formerly CodeWhisperer): AI coding assistant; integrated into IDEs and AWS console. An SA should be aware of how to govern its use (data residency, telemetry opt-out, professional tier for IP indemnification)." The plan's 20 steps do not include any instruction to add Amazon Q Developer governance guidance. For a senior SA skill, governance of AI coding assistants — especially the IP indemnification split between the free tier (no indemnification) and the professional tier (indemnification included) — is a real architecture concern for enterprise customers. This is not a critical gap, but it is a documented researcher finding that the plan silently dropped.

- **Flaw 7 — Step 20 references the Responsible AI Lens with its "10 dimensions" but the plan's list matches the researcher document verbatim without verifying the count:** The researcher cites "10 dimensions: controllability, privacy, security, safety, veracity, robustness, fairness, explainability, transparency, governance." Counting those yields exactly 10, so the number is consistent. However, the plan's step 20 says to add the lens after "the six pillars" in the Well-Architected Framework section. The researcher document is explicit: "Lenses are separate from pillars. The Serverless Lens, SaaS Lens, Data Analytics Lens, and (new 2025) Responsible AI Lens extend the framework for specific domains. Conflating lenses with pillars is a common junior error." The plan's instruction to add the lens reference "After the six pillars" in the WAF section is reasonable but risks the implementer placing it inside the pillar list rather than as a clearly separated subsection. The plan should specify that the Lens subsection must be visually distinct from the pillar list to avoid the conflation error the researcher explicitly warns about.

- **Flaw 8 — The plan does not include "AWS Elastic Disaster Recovery (DRS)" despite the researcher flagging it:** The researcher document lists AWS Elastic Disaster Recovery (DRS) as a key DR service: "Block-level continuous replication of EC2-hosted apps to AWS; pilot-light-based, automated failover." The plan's Step 8 adds Resilience Hub but does not mention DRS. For a skill targeting senior SAs advising on DR strategy, omitting DRS creates a gap for the common "lift-and-shift DR for EC2-based workloads" scenario. This is a minor omission since the skill already mentions FIS and the plan adds Resilience Hub, but DRS is the third leg of the DR tooling stool and the researcher flagged it.

- **Flaw 9 — Step 12's description of S3 Express One Zone as "single-AZ" is technically correct but the plan does not instruct the implementer to flag the durability trade-off:** S3 Express One Zone uses a single AZ by design, which means data is lost if that AZ is permanently destroyed. This is a material trade-off for any senior SA recommending it. The researcher document describes it as "Single-AZ directory bucket with 10x lower latency" without explicitly calling out the reduced durability (11 nines across AZs vs. single-AZ durability). The plan's step 12 says to add S3 Express One Zone for "latency-sensitive workloads" but does not instruct the implementer to note that this trades away multi-AZ durability. A senior SA must call this out when recommending it.

- **Flaw 10 — The plan's "Missing Topic 3" says the skill "has no content on Transit Gateway" but the actual SKILL.md does mention Transit Gateway in two places:** The explorer-confirmed SKILL.md contains: (1) "Avoid overlapping CIDRs if VPC Peering, Transit Gateway, or Direct Connect will be used" in the VPC CIDR sizing section, and (2) "Infrastructure OU — Network account (Transit Gateway, Direct Connect), Shared Services" in the Multi-Account Foundation section. The plan therefore overstates this gap by saying TGW is "entirely absent." The genuine gap is that TGW is mentioned only in passing without a decision framework (when to use TGW vs. peering, the non-transitivity of peering, TGW route table segmentation). The plan's step 11 is still valid and necessary — TGW does need a decision framework — but the plan's "What Is Missing" assessment should have said "no decision framework for TGW" rather than "no content." This is an accuracy issue in the plan's own assessment, not a blocker.

## Suggested Improvements

- **Improvement 1:** In Step 2, split the Bedrock Agents and AgentCore references. Instruct the implementer to write: "Bedrock Agents (agentic loops with tool use — the widely-adopted path) and AgentCore (2025, for production-ready autonomous agents requiring lifecycle management, session memory, and observability — the emerging path for complex agent workloads)." This prevents users from being confused about which API to reach for.

- **Improvement 2:** In Step 7, revise the wording to make the TTL-independence distinction explicit. The skill text should read something like: "Global Accelerator (Anycast static IP, routes at the AWS backbone level — no DNS TTL delays, the true data-plane failover mechanism) and Route 53 ARC (Application Recovery Controller — orchestrates controlled failover of Route 53 routing policies; still DNS-based but with pre-validated readiness checks to prevent premature failover)." This prevents the conflation of the two mechanisms.

- **Improvement 3:** In Step 14, revise the wording to clarify the distinction between EventBridge Scheduler (schedule-type resources, cron/rate, distinct API) and EventBridge event bus rules (pattern-matching). The step should state: "EventBridge Scheduler replaces CloudWatch Events scheduled rules (not event bus rules). It is a distinct resource type with its own API, DLQ, and time-zone support. Do not conflate EventBridge Scheduler with EventBridge event bus rules — they solve different problems."

- **Improvement 4:** Add a Step 21: Add Amazon Q Developer governance guidance to the Security or Multi-Account section. One to two sentences: "Amazon Q Developer (formerly CodeWhisperer) governance: the free tier excludes IP indemnification; the Professional tier includes it. For enterprise customers building with Q Developer in a regulated environment, the Professional tier is required and data residency (telemetry opt-out) should be explicitly configured."

- **Improvement 5:** Add a Step 22 (or fold into Step 8): Add AWS Elastic Disaster Recovery (DRS) to the DR Strategy section as the recommended tool for block-level continuous EC2 replication to AWS, covering the pilot-light-based EC2 lift-and-shift DR use case.

- **Improvement 6:** In Step 12, instruct the implementer to include a durability caveat for S3 Express One Zone: "Note: single-AZ only — data is not replicated across AZs. Suitable for reproducible data (caches, scratch space, ML checkpoint data) where re-generation is acceptable if the AZ is permanently lost. Do not use for primary storage of irreplaceable data."

- **Improvement 7:** In Step 10, add a caveat to the Database Savings Plan percentage: "up to 35% savings (ceiling figure; actual discount varies by service and commitment term — verify current rates at the AWS pricing page before including in a business case)."

- **Improvement 8:** In Step 20, explicitly instruct the implementer to add the Lens subsection as a separate heading (e.g. `### Well-Architected Lenses`) that is clearly not part of the six-pillar list, to prevent the conflation error the researcher document specifically flags as a junior-SA mistake.

- **Improvement 9:** Revise the plan's "What Is Missing — Missing Topic 3" language from "entirely absent from the skill" to "present only in passing without a decision framework." The actual SKILL.md mentions TGW in two places. While Step 11 remains necessary, overstating the gap creates a false picture of the skill's current state and could cause the implementer to duplicate existing content rather than extend it.

## Revised Steps (if applicable)

The following are revised versions of the steps with material precision corrections. Steps not listed here are approved as written.

**Step 2 (Revised) — Bedrock/GenAI section, Agents vs. AgentCore distinction:**
Add a Generative AI / Bedrock Architecture section. Cover: Bedrock overview and VPC endpoint requirement (default API calls traverse the internet; VPC Interface Endpoint required for enterprise security postures), IAM model access model, Knowledge Bases / RAG pattern with vector store options (Aurora PostgreSQL pgvector, OpenSearch Serverless, Bedrock-native), Guardrails for content filtering and out-of-scope request rejection, Bedrock Agents (widely-adopted; agentic loops with tool use) and AgentCore (2025; production lifecycle management, session memory, and observability for complex autonomous agents — the emerging path, not the default first choice), token cost management and model selection trade-offs (Claude Haiku for low-latency high-volume classification; Claude Sonnet for complex reasoning; largest models for highest quality — maps directly to Performance Efficiency + Cost Optimization pillars), and when to choose RAG vs. fine-tuning vs. prompt engineering.

**Step 7 (Revised) — Control plane vs. data plane, Global Accelerator vs. ARC distinction:**
Add to Key Production Gotchas: "Control plane vs. data plane during regional events — during a large-scale AWS event affecting a region, control plane operations (EC2 RunInstances, Auto Scaling triggered scale-out, CloudFormation stack updates) may be impaired before or alongside data plane degradation. Design failover to use pre-provisioned capacity (warm or hot standby) and data-plane routing mechanisms. Two distinct tools: (1) Global Accelerator — static Anycast IPs that route traffic across the AWS backbone to the closest healthy endpoint; failover is Anycast-based with no DNS TTL delay — this is the true data-plane failover mechanism for TCP/UDP workloads; (2) Route 53 Application Recovery Controller (ARC) — orchestrates controlled, readiness-gated failover of Route 53 routing policies; still DNS-based, but with pre-validated readiness checks that prevent premature failover to a degraded region. Use both together for the highest-confidence multi-region failover posture."

**Step 12 (Revised) — S3 Express One Zone durability caveat:**
Expand the Storage section with S3 advanced features. Add S3 Express One Zone (directory bucket, ~10x lower latency than standard S3, higher throughput; single-AZ only — data is not replicated across AZs; suitable for reproducible or regenerable data such as caches, ML checkpoints, and scratch space; do not use as the only copy of irreplaceable data), S3 Object Lock / WORM (compliance requirements — PCI, HIPAA), S3 Replication (CRR for cross-region DR and data residency, SRR for cross-account within-region), and S3 Lifecycle policies (default Intelligent-Tiering for unpredictable access patterns; explicit tier transitions for known access patterns). Add FSx row to storage decision table: FSx for Windows File Server (SMB/AD integration), FSx for Lustre (HPC/ML training data, integrates natively with S3), FSx for NetApp ONTAP (multi-protocol: NFS/SMB/iSCSI), FSx for OpenZFS.

**Step 14 (Revised) — EventBridge Scheduler vs. event bus rules precision:**
Add EventBridge Scheduler to the Messaging and Orchestration table as a new row: "EventBridge Scheduler — cron/rate-based scheduled invocations with time-zone support, DLQ, and flexible recurring schedules. A distinct resource type from EventBridge event bus rules: Scheduler manages scheduled triggers (replaces CloudWatch Events scheduled rules); event bus rules handle event-pattern routing. Do not conflate the two. Preferred over CloudWatch Events scheduled rules for all new scheduled workloads."

## Summary

The plan is technically well-grounded, accurately identifies the genuine gaps in the skill, and its 20 steps are correctly sequenced with no circular dependencies or conflicts. The primary weaknesses are precision issues — most notably the Bedrock Agents / AgentCore conflation risk, the Global Accelerator / Route 53 ARC equivalence conflation risk, and the EventBridge Scheduler / event bus rule distinction — that could cause an implementer to write skill content that is technically imprecise at exactly the senior-SA level the skill targets. These are correctable in-place at implementation time using the revised steps above, and do not require replanning.
