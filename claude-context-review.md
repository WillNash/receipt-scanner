# Plan Review

## Verdict
**APPROVED** — the plan is sound and implementation can begin. No blocking flaws were found. Three minor precision issues and one line-count risk are noted below; all are resolvable during authoring without replanning.

## Flaws Found

- **Flaw 1 — Line count estimate is likely 10–15% low:** The plan estimates 430–480 lines and treats 500 as the soft cap from the researcher. Counting the actual content specified — 11 H2 sections, 16 anti-pattern table rows (each a multi-column pipe row), 8 mindset bullets, 3 code examples (two of which carry both a wrong and correct variant), 8 per-scenario response rules in the How to Respond section, 2 pipe tables in State Management, the project directory tree, the linting YAML block, and the Key Production Gotchas list — a conservative estimate is 500–540 lines once code fences, blank lines, table borders, and the frontmatter block are included. The researcher explicitly states "keep under 500 lines; overflow into sibling files." The plan's own contingency (trim the testing table first) is present and valid, but the implementer must treat the `wc -l` check in the testing strategy as a hard gate, not a formality. If the file exceeds 500 lines, trimming only the 4-row testing table saves approximately 8–10 lines — insufficient if the overrun is 30–40 lines. A more aggressive fallback (trimming the Key Production Gotchas section, which duplicates content already in the Anti-Patterns section) should be named in the contingency.

- **Flaw 2 — Riverpod generated ref types not annotated as generated in Example 1:** The plan's Example 1 uses `DioRef`, `AuthRepositoryRef`, and `NotesRef` as parameter types. These types do not exist in source — they are generated by `build_runner` from the annotated function names. A developer who reads the example without already knowing Riverpod code generation will not understand where these types come from. The Key Production Gotchas section does mention `build_runner`, but the connection between that note and the unknown types in Example 1 is not made explicit. The consequence is a confusing example that will prompt questions the skill is supposed to prevent.

- **Flaw 3 — Anti-pattern 15 remediation has a logic error in the guard flag wording:** The plan states: "Use a `bool _isInitialized = false` flag; guard the body with `if (_isInitialized) return;` then set it to `true`." The guard condition is inverted. If `_isInitialized` starts as `false` and the guard is `if (_isInitialized) return;`, then on the first call (when `_isInitialized` is `false`) the guard does not fire and the body runs — which is correct. But this reads as "if already initialized, return early," which is the intended meaning. Tracing the logic: first call, `_isInitialized = false`, guard `if (false) return` does not fire, body runs, flag set to `true`. Second call, `_isInitialized = true`, guard `if (true) return` fires, body skipped. This is actually correct. However, re-reading the plan's exact wording — "guard the body with `if (_isInitialized) return;`" — this is the correct pattern. No logic error exists. Disregard; this was a false alarm during review.

- **Flaw 4 — `version` field listed as part of "required frontmatter" but researcher only mandates `name` and `description`:** The researcher document states: "YAML frontmatter requires `name` and `description` fields." It does not list `version` as required. Both existing skills include it (`aws-sa` at v1.1.0, `python-dev` at v1.0.0), making it an established convention. The plan correctly includes it and should continue to do so. This is not a flaw in the plan's instruction — including `version` is correct — but the plan's claim that frontmatter has three required fields slightly overstates what the researcher confirmed. The practical consequence is zero; the field should be included regardless.

- **Flaw 5 — No explicit note that `mounted` is a `State` property and does not exist in Riverpod contexts:** Anti-patterns 3 and 4 both prescribe `if (!mounted) return;`. The `mounted` property is defined on `State<T>` and is only available inside a `StatefulWidget`'s `State` class. In Riverpod (where there is no `State` subclass), the pattern does not apply. The plan does not note this scope boundary. A developer reading the skill while working in a Riverpod `AsyncNotifier` or `Notifier` could search for `mounted` and be confused. The researcher document does not call this out either, so this is a gap in both the research and the plan. The consequence is mild confusion for Riverpod-only developers. The remediation is a one-sentence parenthetical in the anti-pattern table: "(applies to `StatefulWidget.State`; in Riverpod, use `ref.read()` in event handlers rather than `ref.watch()` inside async callbacks to avoid acting on a disposed ref)."

## Suggested Improvements

- **Improvement 1 — Add a comment to Example 1 identifying generated types:** Insert a single-line comment above the first provider in Example 1:

  ```dart
  // Ref types (DioRef, AuthRepositoryRef, NotesRef) are generated by
  // build_runner — they do not exist until you run: dart run build_runner build -d
  @riverpod
  Dio dio(DioRef ref) => Dio();
  ```

  This resolves Flaw 2 with no line budget impact beyond two lines.

- **Improvement 2 — Name a second-tier contingency for the line budget:** The plan's current contingency is "trim the testing table." If the file is 30+ lines over budget, also trim the Key Production Gotchas section: most of its entries duplicate content already present in the Anti-Patterns table and the State Management section. Removing the Key Production Gotchas section saves approximately 20 lines with minimal content loss, since the underlying facts appear in the anti-pattern remediations.

- **Improvement 3 — Add a scope note to anti-patterns 3 and 4:** After the Remediation column entry for anti-pattern 3, add a parenthetical: "(applies in `StatefulWidget.State`; in Riverpod contexts, prefer `ref.read()` in event handlers over `ref.watch()` inside async callbacks to avoid acting on a disposed notifier)." This closes the Riverpod scope gap identified in Flaw 5.

- **Improvement 4 — Confirm description character count programmatically at implementation time:** The plan estimates ~620 characters against the 1,024-character limit. The implementation agent should measure the exact count of the drafted `description` string (e.g. `echo -n "..." | wc -c`) before finalising. The planned description is longer than the aws-sa description (~520 characters) due to the more extensive trigger phrase list; a measurement confirms it stays within the limit without relying on the estimate.
