| N | file:line | description |
|---|---|---|
| 1 | `terraform/iam.tf:154` | **Security / IAM mis-permission — TransactWriteItems cross-table.** `handle_delete_receipt` calls `dynamodb.transact_write_items` targeting both the jobs table AND `image_hashes` table (when `image_hash` is set). AWS requires `dynamodb:TransactWriteItems` on every table touched in the transaction. The `ImageHashesDelete` policy (line 154) grants only `GetItem` and `DeleteItem` on `image_hashes` — it is missing `dynamodb:TransactWriteItems`. The delete will fail with `AccessDeniedException` for any receipt that has an image hash, which is every normally-processed receipt. |
| 2 | `lambda/api/handler.py:456-460` | **Correctness bug — unguarded `refreshed["Item"]` after update.** After `update_job(...)` succeeds, the code immediately calls `get_item` and accesses `refreshed["Item"]` with no guard. If the job was concurrently deleted (e.g., a parallel DELETE request that completed between the update and this get), `refreshed` will have no `"Item"` key and will raise an unhandled `KeyError`, returning a 500 with no context. Should be `refreshed.get("Item")` with a 404 fallback. |
| 3 | `lambda/shared/line_items.py:86-95` | **Performance / correctness — unbounded retry loop in `_batch_put`.** The `while pending:` loop retries DynamoDB `batch_write_item` indefinitely when `UnprocessedItems` is non-empty. Under persistent table throttling this loops forever, burning Lambda execution time until the function times out and the SQS message is re-queued. There is no backoff, no retry cap, and no circuit-breaker. Should add exponential backoff and a maximum retry count. |
| 4 | `terraform/iam.tf:84-87` | **Security — over-broad Marketplace permission.** The processor Lambda role includes `aws-marketplace:Subscribe` with `Resource: "*"`. This allows the Lambda execution role to subscribe to paid AWS Marketplace products at arbitrary cost. It should be removed or scoped to specific product ARNs once the Bedrock Anthropic subscription is in place; at steady state this permission is not needed at runtime. |
| 5 | `terraform/iam.tf:169-172` | **Security — over-broad S3 PutObject on API Lambda.** `S3PresignedPut` grants `s3:PutObject` on `${aws_s3_bucket.uploads.arn}/*`, covering all prefixes (`uploads/`, `debug/`, `cropped/`). The API Lambda only needs to sign PUT URLs for the `uploads/` prefix. If the presigned-URL generation logic were exploited or contained a path-traversal bug, an attacker could overwrite debug or cropped objects. Should restrict to `${aws_s3_bucket.uploads.arn}/uploads/*`. |
| 6 | `lambda/processor/handler.py:103-108` | **State management / correctness — race between job creation and S3 trigger.** `_process_s3_record` calls `get_job` first; if the S3 trigger fires before the `put_item` from `handle_upload_url` is visible (DynamoDB eventual consistency, or extreme S3-SQS speed), `existing` is `None`. The code then falls through with `user_id = "unknown"` and `user_email = ""`. Line items and image hashes for that job are stored under `user_id="unknown"`, making them invisible to the real user and permanently orphaned. |
| 7 | `lambda/api/handler.py:267-287` | **Correctness bug — pagination loop includes PENDING/FAILED jobs in page count.** `handle_list_receipts` paginates until it has `RECEIPTS_PAGE_SIZE` results, but its `FilterExpression` only excludes `DUPLICATE`. Every PENDING, PROCESSING, and FAILED job also consumes a slot in the count. If a user has many failed or in-progress jobs, the loop returns fewer than 20 COMPLETE receipts per page even though more exist. The web frontend then additionally filters to COMPLETE client-side (HistorySection line 19), compounding the underfetch. |
| 8 | `mobile_new/lib/features/receipts/presentation/screens/receipts_screen.dart:51-76` | **API contract mismatch — mobile shows PENDING/FAILED receipts, web hides them.** The mobile `receiptsProvider` / `ReceiptsService.fetchReceipts` forwards all jobs from the API (which excludes only DUPLICATE). The web `HistorySection` explicitly filters `r.status === 'COMPLETE'`. A user sees PENDING and FAILED items permanently in their mobile history but never in the web history. The filtering should be consistent — either server-side in the API, or both clients should apply the same client-side filter. |
| 9 | `frontend/src/components/EditModal.vue:75-95` | **State management — `saving` flag never reset on success.** `saving.value` is set to `true` when save starts and only reset to `false` in the `catch` block. On a successful save, `emit('close')` is fired but `saving.value` remains `true`. If the parent delays closing the modal (e.g., for animation), the Save button stays disabled until the component is unmounted. A `finally` block resetting `saving.value = false` is missing. |
| 10 | `frontend/src/components/EditModal.vue:18-19` / `mobile_new/lib/features/receipts/presentation/sheets/edit_receipt_sheet.dart:53-68` | **API contract mismatch — `line_total` dropped on first edit.** The initial Bedrock extraction stores `line_total` inside each item in the `items` JSON blob in DynamoDB. After a user edits a receipt, `EditModal` / `EditableItem.toJson()` only send `description, quantity, package_size, unit_price, price, discount` — `line_total` is never included. After the first PATCH the `line_total` field is permanently lost from the stored items. Any downstream query or export that relies on `line_total` (e.g., `line_items` table via `line_items.py` which writes it) will receive `None` for all edited receipts. |
| 11 | `lambda/api/handler.py:316-341` | **Correctness — `_delete_line_items_for_job` doesn't paginate the query.** The `query` call on `LINE_ITEMS_TABLE` has no `Limit` and no pagination loop. DynamoDB query returns at most 1 MB per call. A receipt with many line items (or items with large fields) could silently truncate, leaving orphaned rows after deletion. The function should loop on `LastEvaluatedKey` the same way `handle_list_receipts` does. |
| 12 | `lambda/processor/handler.py:120-131` | **Race condition — duplicate image hash detection is non-atomic.** The processor reads `lookup_image_hash`, then separately calls `analyze_receipt`, then `store_image_hash`. If two SQS messages arrive concurrently for the same image (e.g., user uploads twice quickly before client-side dedup fires), both look up the hash before either stores it, both find nothing, both process fully, and both mark COMPLETE — two separate charges to Bedrock and Textract for identical receipts. A conditional `put_item` on `image_hashes` (e.g., `attribute_not_exists`) would make the write atomic. |
| 13 | `mobile_new/lib/features/upload/presentation/view_models/upload_view_model.dart:114-115` | **Performance — `uploadAll` fires all uploads concurrently without limit.** `Future.wait(pending.map((u) => _uploadOne(u.id)))` launches every pending upload simultaneously. Each `_uploadOne` reads the full file into memory (`readAsBytes`). With 10 files × up to 20 MB each, the app allocates up to 200 MB simultaneously. On memory-constrained devices this can cause the OS to kill the app. Should use a concurrency-limited pool (e.g., process 2–3 at a time). |
| 14 | `mobile_new/lib/core/network/api_client.dart:22-26` | **Error handling gap — 401 auto-signout fires on every non-auth request error.** The `onError` interceptor signs the user out on any 401 response, including 401s from S3 presigned URL expiry or third-party redirects. However, `_s3Dio` (in `UploadService`) is a separate `Dio` instance that does NOT include this interceptor, so S3 401s are unaffected. The risk is low in practice but the comment says "token is invalid/expired and refresh failed" — the handler should verify the error source is the app's own API before signing out. |
| 15 | `lambda/processor/handler.py:83-88` | **Error handling gap — `job_id` extraction is fragile for unexpected key formats.** `parts = key.split("/"); job_id = parts[2].rsplit(".", 1)[0] if len(parts) >= 3 else key`. If an S3 notification arrives for an object NOT under `uploads/{user_id}/{job_id}.ext` (e.g., a direct S3 upload to an unexpected path), `job_id` would be `parts[2]` or the full key. `_mark_job_failed` would then silently create or overwrite an unrelated DynamoDB item. A format validation (e.g., UUID check) before proceeding would prevent corruption. |
| 16 | `frontend/src/components/UploadSection.vue:32-33` | **Correctness — file deduplication in queue uses name+size only.** Two different files with the same name and size (e.g., `receipt.jpg` at 1.2 MB from different folders) are treated as duplicates and the second is rejected with "already in the queue." This is a false positive that silently blocks a valid upload without an obvious way to override it. A content hash or full path should be included in the dedup key. |
| 17 | `lambda/api/handler.py:108-127` | **Security — JWKS cache is shared across concurrent Lambda invocations but has no lock.** Under concurrent Lambda invocations sharing the same execution environment, two requests could simultaneously enter the `if self._data is None` branch and make two concurrent HTTP requests to Cognito's JWKS endpoint. This is a minor inefficiency and not a correctness issue (both get the same keys), but if the Cognito endpoint rate-limits JWKS fetches this could cause spurious 401s under load. |
| 18 | `mobile_new/lib/features/upload/data/services/upload_service.dart:76-79` | **Correctness — `contentTypeFor` defaults unknown extensions to JPEG.** Any file extension that is not `.png` (including `.webp`, `.gif`, `.bmp`, etc.) is silently treated as `image/jpeg`. The API accepts only `image/jpeg` and `image/png`, so the upload will either succeed with wrong content-type or fail with a 400. The function should throw for unsupported types rather than silently misclassifying them, especially since the mobile size check passes before the content-type is determined. |
| 19 | `terraform/cloudfront.tf:75-85` | **Infrastructure — CloudFront returns `index.html` (HTTP 200) for genuine S3 403 errors.** The `custom_error_response` block maps both HTTP 403 and HTTP 404 to `index.html` with response code 200. This is standard SPA practice, but a real access-denied (e.g., misconfigured bucket policy) is indistinguishable from a missing route — the client silently gets the SPA instead of an error, making infrastructure misconfiguration harder to detect in monitoring. The 403 mapping should use response code 403 with `error_caching_min_ttl = 0`, and only 404 should be mapped to 200/index.html. |
| 20 | `lambda/shared/pricing.py:38-43` | **Correctness — `check_price_sum` silently ignores items with no `price` key.** Items that have no `price` field (e.g., newly added items in EditModal before price is filled in, or items where Bedrock omitted `price`) are excluded from the sum without counting as unparseable. The `unparseable_indices` list only captures items where `price` is present but not parseable. This means the price check can report "ok" or produce a misleading difference even when some items contribute nothing to the sum. |
